# 12 · C 阶段方案 A：程序化能力层

> 实施日期：2026-11-14　·　决策：**先做 A；A 效果确实不够再考虑 C（联网 API）；B（换 7B 基座）暂缓**
> 代码：`app/router.py`（规则+话术）、`app/engine.py`（唯一回复入口）、`scripts/smoke_router.py`（单测）

---

## 一、为什么这么做

`docs/08-真实基线报告.md` 的结论：v5 两版在新留出集 **0 硬伤**，语义却大面积崩溃。
B 阶段把输入链路全修对了（背景 2→1、history 0→5、提醒 6/6），语义**仍无质变**。
所以剩下的是能力问题：1.5B + 307 个独立问法的模板数据，学不会「听懂话」。

关键判断：**身份、时间、边界、记忆这四类意图本来就有确定答案**，
让一个 1.5B 模型去赌概率是架构错误。把它们收回程序，模型只负责闲聊语气。

明确排除「继续补样本重训」：已证明微调方向反了，且在 307 个独立问法的分布上
加几百条变体只会继续背模板（见 `docs/09` 第一节）。

## 二、能力归属表

| 意图 | 归属 | 实现 | 备注 |
|---|---|---|---|
| 身份（你是谁 / 叫什么 / 你是猫吗 / 你会什么） | **程序** | `identity_*` 6 条规则 + 话术池 | 含打字失误容错 |
| 实时（几点 / 星期 / 天气） | **程序** | `realtime_*` 3 条规则 | 明确说看不到，不编造 |
| 边界（代写 / 代发 / 查隐私 / 预测 / 联网） | **程序** | `boundary_*` 7 条规则 | 按意图细分话术，不是统一「我干不了」 |
| 记忆（我周三有什么 / 我一般几点睡） | **程序** | `memory_recall` + `Memory.recall()` | 复述检索到的事实，不重做检索 |
| 低风险玩笑 / 挫败 / 口吻调侃 | **程序** | `chat_*` 3 条规则 | 真实使用里翻车最扎眼的几句 |
| 提醒 | 程序（B 阶段已有） | `ensure_remind_output` | 本阶段未改动 |
| 多轮指代（那它叫什么 / 刚才我说什么了） | **模型** | `ANAPHORA_CUES` 让路 | 规则没有上下文，接不住指代 |
| 闲聊（情绪、近况、道别等） | **模型** | `client.chat()` | 1.5B 只负责接话语气 |

**实测覆盖**（`scripts/smoke_router.py`，seed=42）：

- `dev_v2` 48 题：确定性意图 **25/25 命中**（身份 6、边界 10、记忆 5、实时 4），
  闲聊 12 / 多轮 5 / 提醒 6 **全部 0 命中**（交模型）→ 程序化命中率 **52.1%**
- `real_usage` 10 条真实原句：**9 命中**，仅「明天上早八」交模型
- 题库外同义问法 **13/13 命中**（「报一下你的名字呗」「帮我把这段译成法语」「外头下雨没」等）
- 程序化回复喂给当前 `judge`：**0 硬伤**

## 三、三条硬规矩

1. **规则按语义类别写，绝不硬编码题面。**
   `router.py` 不 import 评测器、不读 `dev_v2` / `real_usage`、不读 `expect`。
   单测用 AST 检查代码字面量里没有完整题面，并用题库外同义问法验证泛化。
   写 `if text == "现在几点了"` 就是换一种形式的开卷考，等于 A-1 白做。
2. **程序化回复不算模型能力。**
   `eval.py` 明细记录 `source` / `programmatic` / `rule`，报告单列命中率与
   「模型回复（未命中题）」的硬伤统计；`make_blind_review.py --collect` 回填时
   按「模型 / 程序化」分组出分。**总体平均分含程序化回复，不能当模型分数用。**
3. **覆盖率不是越高越好。**
   闲聊全用规则接管就退化成规则引擎 + 装饰，而且迟早变成背考题。
   确定性意图之外一律返回 `None` 交给模型，52% 的命中率是刻意的边界，不是待补齐的缺口。

## 四、同构与可回退

A-2 的教训是「评测和软件跑两套输入」让 95% 变废分。方案 A 又引入一条新分叉
（程序化 vs 模型），所以：

- `app/engine.py::respond()` 是 **GUI 与 `scripts/eval.py` 唯一的回复入口**；
  输入构造仍只在 `app/runtime_input.py::compose_turn()`
- `scripts/eval.py --input-mode runtime` 走引擎；`plain` 是 A-2 历史口径，
  **刻意绕过引擎**以复现旧行为，仅供对照
- 双侧都有回退开关：
  - GUI：`慕心.exe --no-router` / `python app/muxin_gui.py --no-router`
  - 评测：`scripts/eval.py --no-router`
- 评测固定 `--seed 42` 时话术选择可复现；GUI 传 `seed=None`，连问两次不会复读同一句

单测第五组验证了回退：开路由时模型调用 0 次，关路由时 1 次。

## 五、已知局限（不要误读成「软件修好了」）

- **闲聊仍是 1.5B 的水平**。方案 A 没有提升模型能力，只是把会翻车的确定性问法挪走了；
  「今天提不起劲儿」「刚跑完步，累但挺爽」这类复合情绪依然容易答偏。
- **规则覆盖不到的问法会露馅**。同义改写靠关键词，没有语义理解；
  用户换个没见过的说法就可能落回模型。
- **程序化回复是设计好的话术池**，天然不会触发自动硬伤判据。
  它的「0 硬伤」不能和模型的「0 硬伤」放在同一张表里比较 —— 这正是分列统计的原因。
- **最终结论仍以人工盲评为准**（`docs/11`）。自动判据只给硬伤下限。

## 六、暂未做、但留了口子的增强

- 实时时间改读系统时钟：当前评测集 `expect` 明确要求「不编造具体时间、说明看不到」，
  所以这一版只做诚实拒答。将来若要报真实时间，需同步改判据（校验回复时间是否等于
  生成时刻）并更新留出集期望，**不能静默打开**。
- 天气 / 联网查询：属于方案 C 的范畴，需要用户就「对话出本机 + 密钥」拍板。
- 更大基座（方案 B）：见 `docs/09` 更正后的硬件结论，**本轮不下载、不启用 LoRA**。
