## 一、为什么必须换能力来源

来自 `docs/08-真实基线报告.md` 的硬证据：

| 现象 | 证据 |
|---|---|
| 微调带来能力损伤 | `real_usage` 里「你是谁」：纯基座答「我是慕心，一只生活在老周电脑上的小猫咪」，v5-fp16 答「我在这儿陪着你，别着凉。」 |
| 训练数据撑不起聊天 | `seed 2391 + train 2145` 去重后**只有 307 个独立问法**，最高频题面出现 35 次 |
| 模型学的是拼句不是理解 | 「刚才被导师夸了」→「赶紧去冲个澡。」；「喵一个」→「别骂我，我没法变。」 |
| 尺度没救 | 旧 95% 里 45% 是开卷考、闲聊 20/20 是白送分；新尺子下 v5 两版 0 硬伤但语义大面积崩溃 |

**B 阶段修的是链路**（双重背景、无关记忆噪声、多轮上下文丢失、提醒兜底、调度状态），
这些能显著减少「被背景带跑」，但**修不了「听不懂这句话」**。
1.5B 的语义理解上限 + 低多样性模板数据，是当前软件不可用性的根因。

**明确排除的一条路**：继续在现有 2145 条数据上补样本重训。
理由：① 已证明微调方向反了；② `real_usage.jsonl` 的 10 条原句必须保持零重叠，
补样本只能用变体，空间很窄；③ 307 个独立问法的分布不改，加几百条仍是在背模板。

## 二、三个方案

### 方案 A · 程序化能力层，本地小模型只负责语气（纯本地，推荐先做）

把**有确定答案的意图**从模型手里收回来，交给程序：

| 意图 | 归属 | 做法 |
|---|---|---|
| 身份（你是谁 / 你叫什么 / 你是猫吗） | 程序 | 固定身份话术池 + 轻量改写，不交给模型 |
| 实时（几点 / 星期 / 天气） | 程序 | 明确说「看不到时间/查不了天气」；需要真实时间时直接读系统时钟 |
| 边界（代写 / 代发 / 查隐私 / 预测） | 程序 | 意图规则命中即拒答，不赌模型会不会编 |
| 记忆（我周三有什么 / 我一般几点睡） | 程序 | 检索 `Memory` 后用模板组装，模型最多润色 |
| 提醒 | 程序（已是现状） | 收紧后的 `ensure_remind_output` 兜底 |
| 闲聊 | 模型 | 1.5B + 人设 prompt，只负责接话语气 |

- **优点**：确定性、可单测、纯本地、响应快、1.5B 够用；身份/边界/实时这些最扎眼的翻车点立刻消失
- **缺点**：闲聊仍然弱；规则覆盖不到的问法会露馅；「像不像在跟模型聊天」取决于闲聊占比
- **工作量**：中（约 1 个意图路由层 + 话术池 + 单测）
- **风险**：低，且随时可回退
- **诚实标注**：这类回复和提醒兜底一样是「程序说的」，评测报告必须单列 `programmatic` 命中率，不能算模型能力

### 方案 B · 换更大的本地基座（纯本地）

- 候选：`Qwen2.5-7B-Instruct` Q4_K_M（约 4.7 GB）、`Qwen3-4B` 量化版
- **停用现有 LoRA**，改用 `SYSTEM_PROMPT` + 少量 few-shot 控制风格；现有微调产物留作教学实验存档
- 配合已加好的 `--gpu-layers`，把部分层卸到 RTX 4060 Laptop 8G
- **优点**：语义理解是质变，仍是纯本地、不联网、无隐私外流
- **缺点**：E 盘多占约 5 GB；下载与验证耗时；纯 CPU 回退时较慢
- **2026-11-14 更正（实测）**：原文「8G 显存放不下 7B 全部层」是**错的**，
  那是按 fp16 权重约 14 GB 估的。实测本机 `nvidia-smi`：RTX 4060 Laptop
  **8188 MiB 显存**、Ryzen 7 8845HS 8 核、23.3 GB 内存、E 盘可用 79.5 GB。
  `Qwen2.5-7B-Instruct` Q4_K_M 约 4.7 GB，**8 GB 显存足以放下全部层**，
  还能留约 3 GB 给 KV cache / 计算缓冲；配合已有的 `--gpu-layers` 可全量 offload，
  首字延迟会明显好于原文估计的 2–4 秒。
  **但「训练」与「运行」必须分开说**：在本机**微调/训练 7B 不可行** —— 全参数需
  60GB+ 显存，QLoRA 4bit 最少约 10–12 GB（8 GB 会 OOM），纯 CPU 训练慢到以周计。
  方案 B 是「换一个量化基座来**推理**」，从来不是在这台机器上训练 7B。
- **工作量**：中（下载 + 量化 + 同尺子验证）
- **风险**：中，主要风险是「速度体验」而不是「效果」

### 方案 C · 联网大模型 API（效果最好，需拍板）

- 主能力交给云端大模型；本地程序继续负责提醒调度、记忆检索、隐私过滤与离线兜底
- **优点**：聊天质量质变，本地几乎不用调模型；开发量最小
- **缺点**：要联网、要账号与密钥、有调用费用、对话内容出本机
- **需要你确认的三件事**：
  1. 是否接受**对话内容发送到云端**
  2. 是否愿意配置 API 密钥（以及用哪家）
  3. 断网时是否允许降级到本地 1.5B（体验会明显落差）

## 三、组合与推荐

| 目标 | 推荐路径 |
|---|---|
| 坚持纯本地、想尽快能用 | **A 先做 → 用同一把尺子验收 → 收益不够再上 B** |
| 坚持纯本地、追求聊天质量 | **A + B**：程序层兜确定性意图，7B 负责闲聊 |
| 接受联网 | **C + A**：云端负责语义，程序层负责提醒/记忆/隐私，且把身份、边界这类仍留在本地 |
| 想学「怎么把一个模型项目做对」 | **A 最值钱**：它逼你把「能力该归程序还是归模型」这条边界画清楚，这正是本项目前几版一直没做对的事 |

**我的推荐：先做 A，暂不下载 7B、暂不接 API。**（用户已按此拍板）
理由：A 不花钱、不联网、可回退，而且能先把「评测尺子」和「能力归属」这两件事收口；
做完用 `dev_v2 + real_usage + 人工盲评` 量一次，再判断缺口是否真的需要 C。
直接上 7B 会同时引入下载、速度、显存三个新变量，问题会混在一起说不清。

> 用户补充的优先级：**A 效果确实不好 → 考虑 C（联网 API），不是 B**。
> B 本轮只回答了硬件可行性问题，暂缓实施。

## 四、无论选哪条，验收口径不变

1. 用 `dev_v2.jsonl`（48 条）+ `real_usage.jsonl`（10 条真实原句），`--input-mode runtime`
2. `--tag` 区分版本，**不覆盖** A-3 / B 阶段的历史明细
3. 判据改动一律走 `scripts/rescore.py` 离线重算，保证跨版本同尺子
4. 自动判据只给「硬伤下限」，**最终结论以人工盲评 0/1/2 为准**
5. 程序化回复必须单独统计命中率，不许和模型能力混算
